## TicketHub System Design

## 1. Requirements

### Functional requirements

- Visitors can browse and search concerts and events by artist, venue, date, and location.
- Customers can view event details, prices, and a current seat map with available, held, and sold seats.
- Customers can sign up, sign in, manage their account, and view their orders.
- A customer can temporarily hold one or more available seats while completing checkout.
- Customers can pay for a held seat and receive a confirmed order and ticket with a scannable barcode.
- Customers can retrieve, cancel, or request a refund for tickets according to the event's policy.
- Event managers can create events, configure prices and seat inventory, and view sales.
- Staff can scan tickets at entry and verify that a ticket is valid and has not already been used.

### Non-functional requirements

- **Correctness:** A seat can be sold to at most one customer. Orders, seat state, and payment state must be recoverable and auditable.
- **Availability:** Browsing and event information remain available during partial service failures. Checkout may temporarily reject requests rather than risk duplicate sales.
- **Performance:** Typical event pages should load in under 2 seconds; seat-hold and checkout APIs should return within 1 second excluding the external payment provider.
- **Scalability:** Handle normal browsing traffic and short, intense on-sale bursts by adding stateless app instances and buffering noncritical work.
- **Security:** Require authenticated checkout, encrypt sensitive data in transit and at rest, use a PCI-compliant payment provider, and never store card numbers or security codes.
- **Durability and recovery:** Persist orders and inventory changes, back up the database, and use payment-provider idempotency to safely retry payment operations.
- **Fairness and abuse resistance:** Rate-limit hold attempts, limit the number of seats per order, and expire abandoned holds promptly.

## 2. Traffic and Capacity Estimates

Use the supplied workload facts: TicketHub has 2 million registered users; on a normal day, 50,000 people visit and each views 10 pages; 5,000 tickets are sold. During a popular concert on-sale, 200,000 people try to buy 20,000 seats within the first 10 minutes. Daily averages divide by 86,400 seconds; the on-sale average divides by 600 seconds. These averages do not capture short spikes within the sale window.

- **Normal-day active share:** `50,000 ÷ 2,000,000 = 2.5%` of registered users visit on a normal day.
- **Normal page views:** `50,000 × 10 = 500,000` page views/day, or `500,000 ÷ 86,400 = 5.8` page views/second averaged across the full day.
- **Normal ticket sales:** `5,000 ÷ 86,400 = 0.058` tickets/second averaged across the full day, equivalent to 5,000 tickets/day. This is not a per-second prediction for actual sales hours.
- **Popular on-sale arrivals:** `200,000 ÷ 600 = 333` people/second on average during the first 10 minutes.
- **Supply and demand:** `200,000 ÷ 20,000 = 10` people competing for each seat. If all 20,000 seats sell evenly across the 10-minute window, that is `20,000 ÷ 600 = 33.3` successful ticket sales/second on average. Assuming each person tries for one seat, at most 10% can succeed; multi-seat requests or retries change the request volume, not the 20,000-seat cap.
- **Request-rate implication:** The facts give page views and sale participants, not the number of API calls generated by each page or purchase attempt. Therefore exact API requests/second cannot be derived. If each sale participant generates one hold request, the average is about 333 hold attempts/second; seat-map polling, checkout calls, and retries increase total API traffic. Load-test above that baseline and rate-limit or queue admission during launch spikes.

Cache static assets and event details where appropriate, but always read and change live seat availability through the authoritative inventory database. Holds, checkout, and final availability checks must not be served from a stale cache.

## 3. API

All endpoints use HTTPS and JSON. Customer endpoints require a bearer access token except event browsing. Mutating requests accept an `Idempotency-Key` so client retries do not create duplicate holds, orders, or charges.

| Method and endpoint | Purpose |
| --- | --- |
| `GET /v1/events?query=&date=&location=` | Search published events; returns event summaries and pagination. |
| `GET /v1/events/{eventId}` | Get event details, venue information, and pricing sections. |
| `GET /v1/events/{eventId}/seats` | Get a seat map with a best-effort availability snapshot; not a reservation. |
| `POST /v1/events/{eventId}/holds` | Atomically hold requested seat IDs for the authenticated customer; returns a hold ID and expiry or a conflict if any seat is unavailable. |
| `DELETE /v1/holds/{holdId}` | Release the customer's active hold early; expired holds are released automatically. |
| `POST /v1/holds/{holdId}/checkout` | Create an order and initiate payment for the held seats; retries with the same idempotency key return the same result. |
| `GET /v1/orders/{orderId}` | Retrieve order, payment, and ticket status for its owner. |
| `POST /v1/tickets/{ticketId}/scan` | Staff-only check-in operation; atomically marks a valid ticket as used and rejects repeat scans. |

Hold and checkout failures use meaningful status codes: `409 Conflict` for unavailable seats or expired holds, `401 Unauthorized` for missing authentication, and `429 Too Many Requests` for rate limits.

## 4. Data Model

Use a relational database such as PostgreSQL as the source of truth for inventory, holds, and orders. Primary keys are UUIDs; foreign keys enforce relationships.

| Table | Important columns and constraints |
| --- | --- |
| `customers` | `id` (PK), `email` (unique), `password_hash`, `created_at` |
| `events` | `id` (PK), `venue_id` (FK), `title`, `starts_at`, `status` |
| `venues` | `id` (PK), `name`, `address` |
| `event_seats` | `id` (PK), `event_id` (FK), `seat_label`, `price`, `state`, `hold_id` (nullable FK), `hold_expires_at`; unique (`event_id`, `seat_label`) |
| `holds` | `id` (PK), `customer_id` (FK), `event_id` (FK), `status`, `expires_at`, `idempotency_key`; unique (`customer_id`, `idempotency_key`) |
| `orders` | `id` (PK), `customer_id` (FK), `hold_id` (unique FK), `status`, `total_amount`, `created_at` |
| `order_items` | `id` (PK), `order_id` (FK), `event_seat_id` (FK), `unit_price`; unique (`event_seat_id`) |
| `payments` | `id` (PK), `order_id` (FK), `provider_reference` (unique), `status`, `amount`, `idempotency_key` (unique) |
| `tickets` | `id` (PK), `order_item_id` (unique FK), `barcode` (unique), `status`, `checked_in_at` |

Relationships: one venue has many events; one event has many event seats and holds; one customer has many holds and orders; one hold can produce at most one order; one order has one or more order items and payment attempts; each order item references one event seat and produces at most one ticket. A unique `order_items.event_seat_id` prevents a seat from appearing in two completed orders.

### Preventing duplicate seat sales

The `event_seats` row is the single authoritative record for each seat at each event, protected by unique (`event_id`, `seat_label`). A hold request runs in a database transaction and conditionally updates each requested seat only if it is `available` (or its previous hold has expired). The update changes it to `held`, attaches the new `hold_id`, and sets an expiry. The database locks the updated row: if two customers race for the same seat, one update succeeds and the other sees zero rows updated and receives `409 Conflict`. For a multi-seat request, update all requested seats in one transaction; if any seat cannot be acquired, roll back the entire transaction.

Checkout first rechecks the active hold in a database transaction, creates a `pending_payment` order, and starts an idempotent payment-provider request while the seats remain held. A signed provider webhook (or a verified provider status lookup) confirms the result. On success, a transaction changes each seat from `held` to `sold` only if the hold ID still matches and the hold has not expired, then marks the order paid and creates tickets. If payment fails, the order is marked failed and the hold is released or allowed to expire. If payment succeeds after the hold expired or the seats were reassigned, do not issue tickets: void or refund the charge and flag the order for reconciliation. The unique order-item constraint is an additional safeguard. Expiration workers release stale holds, while the conditional update also treats an expired hold as reclaimable so correctness does not depend on the worker running on time.

## 5. Architecture

```text
[Web / Mobile Clients] --> [CDN + WAF] --> [Load Balancer / API Gateway]
						      |
					      [Stateless App Servers] <--- [Payment Webhooks]
						 /       |        \                 ^
				   browse/cache    inventory     checkout         |
				      |               |              |             |
				  [Redis]      [Primary SQL DB]   [Payment Provider]
							 |              |
						 [Read Replica]       +-- payment status
							 |
						  [Event Queue]
							 |
					   [Email / Ticket Workers]

[Staff Scanner] --> [API Gateway] --> ticket validation in [Primary SQL DB]
```

- **Web and mobile clients:** Browse events, show seat maps, and perform authenticated checkout. They treat seat-map availability as a snapshot until a hold is confirmed.
- **CDN and WAF:** Deliver static assets and absorb/cache public event content; filter common malicious traffic and provide edge rate limits. Do not cache authoritative hold or checkout responses.
- **Load balancer and API gateway:** Route requests to healthy application instances, terminate TLS, enforce request limits, and validate tokens.
- **Stateless app servers:** Implement event browsing, hold workflows, orders, and staff APIs. They can scale horizontally; all authoritative state lives outside the instances.
- **Redis cache:** Cache event descriptions and other noncritical read data. It is not the lock or source of truth for seat ownership.
- **Primary SQL database:** Enforce transactional seat claims, uniqueness, order integrity, and ticket check-in. All inventory mutations go here.
- **Read replica:** Serve browse and reporting queries where slight replication lag is acceptable. Holds and checkout use the primary database.
- **Payment provider:** Collects payment details and processes charges so TicketHub does not store card data. Idempotency keys and webhook reconciliation handle retries and asynchronous outcomes.
- **Event queue and workers:** Send confirmations, generate ticket documents, and process other retryable work without slowing checkout. Queue consumers must be idempotent.
- **Staff scanner:** Uses an authenticated staff endpoint to validate and atomically check in tickets against the primary database, preventing a barcode from being accepted twice.

## 6. Trade-offs

- **Strict inventory consistency vs. checkout availability:** All seat claims go through the primary database, preserving the no-double-sale guarantee but making that database a critical dependency. During a primary outage, TicketHub should fail closed for holds and checkout rather than risk overselling; cached event browsing can continue.
- **Temporary holds vs. friction and inventory utilization:** Holds give customers time to pay and reduce checkout races, but abandoned holds temporarily hide seats from other buyers. Short expirations, clear countdowns, per-customer limits, and cleanup reduce the impact; too-short expirations can punish slow payment flows.
- **Relational transactions vs. write scaling:** A relational database makes seat uniqueness and multi-seat transactions straightforward and auditable, but a single event can concentrate writes on a small set of rows. Load tests, connection pooling, careful transaction duration, and partitioning by event can help; splitting seat ownership across independent stores would make correctness harder.
- **Cached seat maps vs. freshness:** Cached maps reduce read load during a sale, but can show a seat as available after it has been held. Mark the map as a snapshot, revalidate atomically on hold, and return current seat state after conflicts; never promise a seat based only on cached data.
